Changelog das mudanças e roteiro de testes para você validar antes do merge/deploy.

Branch: codex/0.1-password-reset-email Commit: fix(auth): entregar e-mails de reset de senha com segurança

1. O que mudou (resumo)

Objetivo: um usuário com senha consegue recuperar acesso sozinho via e-mail, sem expor token nem confirmar se a conta existe.

1. Login → “Esqueci a senha” → informa e-mail
2. API gera token (hash no banco) e envia e-mail com link /reset-password?token=…
3. Usuário define nova senha → sessões antigas são invalidadas

3. Pré-requisitos de ambiente

  • FRONTEND_URL apontando para o app web (ex.: http://localhost:5173) — usado no link do e-mail.
  • Em produção/staging: RESEND_API_KEY (+ RESEND_FROM) ou SMTP (SMTP_HOST, etc.). Sem isso o reset falha de propósito.
  • Em desenvolvimento: sem mail configurado o envio vira no-op (log), útil para testes unitários — para validar e-mail real, configure Resend/SMTP localmente.
  • API e Web rodando (ex.: ports 3000 e 5173).

5. Checklist manual — o que você deve validar

Marque mentalmente cada item após testar no browser / API.

Fluxo feliz

  • Abrir /login e ver o link Esqueci a senha apontando para /forgot-password.
  • Informar um e-mail de conta com senha existente → ver mensagem genérica de sucesso (mesmo texto se o e-mail não existir).
  • Receber o e-mail (Resend/SMTP) com link contendo /reset-password?token= e TTL comunicado (~1h).
  • Abrir o link, definir senha válida (mín. 8 chars, letra + número) e ver sucesso.
  • Entrar no login com a nova senha.
  • Confirmar que sessões antigas foram derrubadas (refresh/cookie antigo deixa de funcionar).

Segurança / anti-abuso

  • E-mail inexistente: mesma mensagem de sucesso; nenhum e-mail enviado.
  • Conta só Google (sem passwordHash): sem e-mail de reset.
  • Token raw nunca aparece em logs da API, resposta HTTP ou mensagens de erro.
  • Reutilizar o mesmo link depois do reset → erro (token inválido/expirado).
  • Link sem ?token= em /reset-password → estado de link inválido.
  • Rate limit: várias chamadas rápidas a forgot/reset → throttling (3/min forgot, 5/min reset).

Produção / configuração

  • Com NODE_ENV=production e sem Resend/SMTP: forgot-password responde indisponível (503 genérico), sem vazar se a conta existe.
  • Link do e-mail usa o domínio correto de FRONTEND_URL (não localhost em produção).
  • i18n: conta com locale en recebe e-mail em inglês; UI PT/EN coerente.

UI / UX

  • Validação client: e-mail inválido no forgot; senha fraca / confirmação diferente no reset.
  • Links “Voltar ao login” nas páginas forgot e reset.
  • Mobile: formulários usáveis na viewport pequena.

6. Sugestão de smoke via API (opcional)

# 1) Pedir reset (deve retornar 202 + mensagem genérica)
curl -i -X POST "$API/auth/forgot-password" \
  -H 'Content-Type: application/json' \
  -d '{"email":"seu-usuario@exemplo.com"}'

# 2) Após pegar o token do e-mail (NUNCA logar em CI/produção):
curl -i -X POST "$API/auth/reset-password" \
  -H 'Content-Type: application/json' \
  -d '{"token":"TOKEN_DO_EMAIL","newPassword":"NovaSenha1"}'

# Esperado: 204 No Content
