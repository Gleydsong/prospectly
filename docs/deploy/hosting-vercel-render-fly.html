Render, Vercel ou Fly.io — onde o sistema inteiro cabe de verdade

Análise após sincronizar o repositório local com origin/main via GitHub MCP. Conclusão: a Vercel é excelente para landing Next.js e SPA Vite, mas não hospeda o sistema completo sem reescrever a API. A Render já encaixa. Fly.io é a terceira plataforma em que o monorepo cabe nativamente e escala nos dois eixos.

Veredito

Não mover todo o Prospectly para a Vercel. Landing (apps/landing, Next.js 15) e web (apps/web, Vite estático) cabem bem. A API NestJS com Prisma, Redis, BullMQ in-process, webhooks raw body, CSV de 5 MB e Opportunity Finder/Qwen via Ollama é um processo sempre ligado — o modelo da Vercel continua sendo Function com duração máxima, corpo de 4,5 MB e sem worker persistente.

Manter a Render no curto prazo é o caminho de menor risco: o blueprint já descreve API Docker, web estática, landing Node, Postgres 16 e Key Value Redis. A plataforma já oferece escala vertical (compute plan) e horizontal (até 100 instâncias; autoscaling no plano Pro+).

Terceira alternativa recomendada: Fly.io. É a única das três em que o Dockerfile atual (targets api e worker) vira process groups, com fly scale count (horizontal) e fly scale vm / fly scale memory (vertical) independentes por processo. Também admite GPU para Ollama/Qwen3 8B, que nem Vercel nem o blueprint atual da Render cobrem.

O que o sistema é hoje

Monorepo pnpm com três apps implantáveis. Workers BullMQ ainda rodam no mesmo processo HTTP da API em produção. O Compose já tem target worker; o Blueprint da Render ainda não. Região: Frankfurt. Cookie de refresh já é SameSite=None; Secure porque API e web estão em hosts distintos em onrender.com.

Comparativo das três plataformas

Vercel

Melhor CDN/DX do mercado para Next e estáticos. Fluid Compute alonga Functions (até 800s / 1800s beta), mas não substitui Nest + BullMQ always-on.

Render — prós e contras

Prós
  • Blueprint já existe: API Docker, web static, landing Node, DB, Redis.
  • Processo always-on: Nest, Prisma, Helmet, raw webhooks e BullMQ funcionam sem adapter.
  • Escala vertical oficial: troca de compute plan (CPU/RAM).
  • Escala horizontal oficial: 1–100 instâncias; load balancer nas web services.
  • Background Worker nativo para o split documentado em docs/deploy/workers.md.
  • Rede privada entre API, Postgres e Key Value; Redis noeviction correto para BullMQ.
  • autoDeployTrigger: checksPass já amarra CI do GitHub.
  • Domínio prospectlyonboard.com e cookie cross-site já operacionais.
Contras
  • Plano atual da API é starter (0,5 CPU / 512 MB) com HTTP + filas no mesmo processo — aperto real.
  • Postgres basic-256mb / 5 GB: teto cedo para CRM + buscas + RLS.
  • Autoscaling horizontal exige workspace Pro ou acima.
  • Worker dedicado ainda é proposta; escalar a API hoje escala também os consumers.
  • CDN/edge da landing e da SPA é mais fraco que o da Vercel.
  • Sem GPU: Opportunity Finder com Qwen3 8B local não mora aqui.
  • Cold start some no Starter pago, mas deploys e região única (Frankfurt) limitam latência BR.
  • Hosts *.onrender.com são public suffix — cookie exige SameSite=None até haver domínio próprio no app/API.
Implicação

A Render já tem os dois eixos de escala. O gap não é a plataforma, é o desenho atual: worker inline + planos pequenos. Antes de migrar de hospedeira, o maior ganho é subir compute da API/DB e publicar prospectly-worker.

Vercel — prós e contras

Prós
  • Landing Next.js 15 é cidadã de primeira classe (App Router, previews, rollback, Firewall).
  • SPA Vite vira Static com rewrite — mesmo padrão da Render, com CDN global melhor.
  • Fluid Compute: concorrência na mesma instância, menos cold start, waitUntil.
  • Duração de Function: Hobby 300s; Pro/Ent 800s (1800s beta) — melhor que o serverless antigo, ainda finito.
  • Escala horizontal automática de invocações (até 30 000 Hobby/Pro).
  • Marketplace: Postgres (Neon) e Redis (Upstash) em poucos cliques.
  • Preview por PR acelera landing e web sem Blueprint extra.
  • Há guia oficial “Deploy NestJS to Vercel” — para APIs adaptadas a Functions, não para este runtime.
Contras
  • Documentação oficial: backends precisam abandonar “long-running background servers”.
  • BullMQ consumidor precisa de processo vivo + Redis persistente. Function morre no maxDuration.
  • Cron e Workflows da Vercel não substituem as quatro filas + reconciliadores atuais.
  • Body/response de Function = 4,5 MB. CSV default do Prospectly = 5 MB → 413.
  • Memória vertical da Function: no máximo 4 GB / 2 vCPU no Pro. Sem “subir a máquina”.
  • Prisma em Function exige pooler; rajadas de conexão quebram Postgres pequeno.
  • Ollama/Qwen3 8B não roda. Opportunity Finder ficaria só no fallback determinístico ou API externa.
  • Docker na Vercel alimenta Functions/container images, não um CMD node dist/main.js always-on como o Dockerfile atual.
  • Webhook Asaas precisa responder 200 rápido; jobs longos de OSM/Overpass não cabem no request HTTP.
  • Migrar “tudo” implica reescrever API (fila → Workflow/QStash, uploads → S3, IA → provedor remoto).
Uso honesto

Híbrido faz sentido: Vercel = landing + web, Render ou Fly = API + worker + Postgres + Redis. Isso pega o CDN/DX da Vercel sem fingir que Nest+BullMQ é serverless. Cookie cross-site continua; o conserto estrutural é app. + api. no mesmo eTLD+1.

Terceira alternativa: Fly.io

Escolhida porque o Prospectly já é um sistema de containers com dois processos (apps/api/Dockerfile targets api e worker, Compose profile full). Fly Machines são VMs que rodam essa imagem. Escala horizontal e vertical são comandos de primeira classe, por process group — o requisito pedido.

Prós
  • Docker sem adapter: o Dockerfile de produção atual é o artefato de deploy.
  • Horizontal: fly scale count api=3 worker=2 — HTTP e fila sobem separados.
  • Vertical: fly scale vm performance-2x --process-group worker e fly scale memory.
  • Autoscale por métrica e stop/start de Machines (capacidade de pico barata quando parada).
  • Health checks equivalentes a /health/ready.
  • Fly Postgres + Redis/Upstash; rede privada entre apps.
  • Multi-região (ex.: gru São Paulo + fra) sem trocar de produto.
  • GPU Machines para Ollama/Qwen3 8B no mesmo provedor da API — único dos três com esse encaixe.
  • Volumes se um dia houver cache OSM/modelos; sem volume, Machines continuam stateless como hoje.
Contras
  • Não está em produção hoje: DNS, secrets, webhooks Asaas e CI teriam cutover.
  • DX de preview por PR é mais fraca que Vercel (dá para montar, não é default).
  • Landing Next no Fly perde ISR/CDN/Firewall da Vercel, a menos que o front fique híbrido.
  • Fly Postgres é operacionalmente mais “você no comando” que o managed da Render.
  • Curva de fly.toml, process groups e IPs 6PN — maior que o Blueprint atual.
  • Preço de Machines always-on + GPU pode passar a Render Starter rápido (compensa só com carga/IA real).
  • Região BR (gru) vs dados hoje em Frankfurt: latência e LGPD/residência precisam de decisão explícita.
Por que não Railway / Cloud Run / ECS

Railway é parente da Render (bom DX, H+V mais limitado, sem GPU de primeira). Cloud Run escala horizontalmente muito bem, mas CPU some sem request e worker vira min-instances + outro serviço. ECS/Fargate tem os dois eixos e GPU, com custo de operação AWS demais para o estágio atual. Fly.io é o meio-termo: Docker que já temos + escala H/V + GPU sem virar plataforma interna.

Escala vertical vs horizontal no Prospectly

Eixo O que dói hoje Render Vercel Fly.io
Vertical OSM/Overpass + Cheerio + Prisma + BullMQ no mesmo 512 MB; Qwen 8B precisa de RAM/GPU. Trocar plan da API/worker/DB. Teto 4 GB Function. Sem GPU. VM maior só no worker ou só na API; GPU à parte.
Horizontal Vários tenants buscando ao mesmo tempo; filas profundas. N instâncias + LB. Sem worker split, replica também o consumer (risco de over-consume se mal configurado). Milhares de invocações — inútil se cada uma não drena a fila. scale count por grupo; worker N, API M.

O que teria de mudar para “ir para a Vercel”

  1. Reescrever a API para o adapter de Functions (sem app.listen persistente).
  2. Tirar processors do AppModule e trocar BullMQ por Workflows/QStash/outro worker fora da Vercel.
  3. Colocar Prisma atrás de pooler; revisar RLS + conexões por invocação.
  4. Baixar CSV_MAX_FILE_SIZE_BYTES para ≤ 4,5 MB ou mandar upload direto a object storage.
  5. Apontar Opportunity Finder / WhatsApp AI para API remota (OpenAI-compatible). Abandonar Ollama local.
  6. Revalidar webhooks Asaas (200 rápido + trabalho assíncrono externo).
  7. Recriar CORS, cookies e domínios. Landing e web na Vercel; API em outro host.

Isso não é troca de hospedeira. É redesign do runtime. Custo alto, ganho concentrado no front.

Roteiro recomendado (sem migrar agora)

  1. Agora na Render: medir CPU/RAM/fila em /api/v1/ops/metrics. Se 512 MB saturar, subir API para 1c-2g e Postgres para ≥ 1 GB.
  2. Aprovar o worker: publicar prospectly-worker (já especificado). Aí a escala horizontal da Render passa a fazer sentido.
  3. Domínio próprio do app: app.prospectlyonboard.com + api. no mesmo registrante, cookie Lax, sem depender de public suffix.
  4. Híbrido opcional: mover só landing (e depois web) para a Vercel. API permanece.
  5. Se a hospedeira da API for trocada: destino é Fly.io, não Vercel. Levantar fly.toml com processes api/worker, Postgres, Redis, secrets Asaas, cutover de webhook e DNS. GPU só quando Qwen em produção for requisito, não default.
